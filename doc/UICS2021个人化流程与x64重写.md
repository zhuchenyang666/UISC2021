# 龙江银行 UICS2021 个人化源码梳理与 x64 重写设计

本文覆盖 MakeCard.exe 的个人化数据准备，以及 HBW0001.dll 从 `MakeCard_Run` 到接触式个人化结束的主链。源码基线为 `Build1-01-2026-09-28/src/HBW0001_龙江银行双算法UICS2021`。线上工艺以银行交付清单、UICS2021 项目适用版本和芯片方确认件为准。下文的样例验证为离线字节检查，读卡器、实卡和 HSM 行为均为静态追踪。

优先重写**只读文件解析**，让 MakeCard 的准备界面和制卡入口共用一份解析结果。旧入口的兼容层负责标签封装、回调和返回码映射。设备会话、卡片流程和密码运算分别拥有独立接口，国密原语由现有自研库提供。

## 1. 入口及数据流

```text
选择 ICP* 二进制个人化文件
  -> MakeCardDlg::OnPrepareData
     -> HBW0001!GetRecordTotalNum / GetDGIList / bGetCpsRecord
     -> 卡面和磁条字段 + 记录号 + 显示账号 + pDataEmv
  -> MakeCardDlg::OnMakeCard
     -> 打开 PC/SC 读卡器
     -> HBW0001!MakeCard_Run(pData = pDataEmv, 回调 = RunAPDU / WriteHBLog)
        -> 准备 CREADER 和配置，按模式接通 HSM
        -> MakeCard_PersonalIC 解开 CARDDATA，定位 EMV / AID / DGI
        -> CREADER::bGetDGI 建立卡片应用所需数据
        -> HD01 Plus 安装 / 接触目录 / 非接触目录 / 借记应用
        -> 联机分支的卡片收尾
        -> 关闭 HSM，返回阶段状态
```

旧界面称为“发卡准备”的步骤实际是**读取、拆分、封装**银行已生成的个人化数据。整文件解密代码已注释。应用配置、TLV 整理和敏感 DGI 处理发生在 DLL 的后续阶段。

## 2. MakeCard.exe 个人化数据准备

### 2.1 准备按钮

依据 `MakeCard/MakeCardDlg.cpp:553`、`:633–740` 与 `HBW0001.cpp:102–345`。

1. 文件选择器按 `ICP*` 过滤，也可选任意文件。打开使用 `rb`，以 `fseek/ftell/fread` 读入完整文件。
2. 从 DLL 解析 `GetRecordTotalNum`、`GetDGIList`、`bGetCpsRecord` 和 `MakeCard_Run`。准备流程实际只填 `cpsRecord[0]`。全局 `g_nRecordNum` 初始值也是 1。
3. `GetRecordTotalNum` 固定写 1。EXE 传入的 `nLen` 此前是文件字节数，调用后被覆盖成记录数。DLL 的第一个形参是 `BYTE*&`，EXE 函数指针声明为 `BYTE*`，当前实现没访问该参数，掩盖了 ABI 不匹配。
4. `GetDGIList` 固定写 `<KEKDATA></KEKDATA><DGIDATA></DGIDATA>`。它不从 EMV 提取实际 DGI 清单。EXE 取得该函数指针后直接调用，漏了空指针检查。两个准备函数的返回状态均未检查。
5. `bGetCpsRecord` 从 `pData` 读取记录序号、卡面和磁条，把整条记录转为 ASCII 十六进制并写入 `pDataEmv`，将 `pData` 前进到本记录声明的尾部，将 `*iDataLen` 置 0。它通过指针读取内容，缺少文件总长边界。
6. PAN 初次由 PRN 中第一个 `|` 前的字段得到，有 `=` 时取其前缀，并去首尾空白。准备完成后 EXE **用文件名去掉前三个字符**覆盖记录中的 PAN。随附样例的字母前缀有 6 个字符，去掉 3 个后仍有字母。界面显示和发卡查找目前因此可能使用文件名派生串。
7. EXE 释放文件缓冲区，后续使用记录内部的 `pDataEmv`。旧结构体仍保留悬空 `pData`。短读和记录解析失败路径未释放已分配的文件缓冲区。失败时界面列表与全局记录也可能不同步。

MAG 通过 `|` 读取三个标志及三个值。样例分列长度为 `1, 1, 1, 0, 48, 112, 0`，含空列和尾部分隔符。离线分支对前两个值位置做旧式解密并写调试日志，注释所称磁道编号与变量名及样例位置有出入。该解密结果未回写原记录，也未传给制卡入口。联机分支在此处为空。**待确认**磁道编号与空列语义，以及产线是否有独立磁条工序。重写准备器可先保留原始 MAG 字节并停止记录明文磁道。

### 2.2 EXE 向制卡入口交付的内容

`CCommFuntion.cpp:6–15` 的 `bFormatData` 用 `strcpy` 覆盖目标。故 `bGetCpsRecord` 先复制的 `COMMData` 在下一次调用即被覆盖。按旧代码实际输出，以及项目《个人化数据接口样例》，向 `MakeCard_Run` 交付的是以 NUL 结尾的窄字符文本：

```xml
<PBOCDATA><CARDDATA>…整条二进制记录的十六进制文本…</CARDDATA></PBOCDATA>
```

`CARDDATA` 覆盖从记录序号起算的 `19 + recordBodyLength` 字节，包含 PRN、MAG、EMV 和样例中的记录尾部。它保留原始字段值。样例 XML 字符串长度为 7120（7078 个十六进制字符和 42 个标签字符），另需 1 字节 NUL。DLL 仅按字面查找 `CARDDATA` 标签，缺少对外层结构、重复标签和目标容量的验证。重写时由兼容层按已确认协议读写窄字符封装，核心直接接收带长度的字节视图。

`OnMakeCard` 用文本框内容在记录中做字符串匹配，查不到时索引仍为 0，存在误选记录的风险。该入口把 PAN 和整个封装文本写入日志。只有 DLL 返回 0 才更新列表为“已发卡”，失败时只弹通用提示。重写应使用准备时确定的记录 ID，并在准备失败、找不到记录、选择过期时禁止开始。

## 3. 记录和 EMV 分段

以下偏移从 0 起算。整数均按源码的逐字节运算解释为大端。二进制字段长度以字节计，ASCII 十六进制长度每字节占两个字符。

| 偏移或位置 | 宽度 | 含义和样例 |
| --- | ---: | --- |
| 0 | 4 | 记录序号，重写用无符号 32 位值，避免旧乘法折入有符号范围 |
| 4 | 10 | 借记卡类别字段，旧代码跳过；注释提到的贷记卡 4 字节格式需另有版本约定 |
| 14 | 1 | ASCII 制卡类型；旧注释 I/F/C 对应纯 IC、复合、磁条，样例为 F；此入口读出后未据此分流 |
| 15 | 4 | 记录体长度，样例 3520；结束位置为 3539 |
| 19 | 6 + 4 + 66 | `000PRN`、段长度、卡面值区 |
| 95 | 6 + 4 + 169 | `000MAG`、段长度、磁条值区 |
| 274 | 6 + 4 + 3215 | `000EMV`、段长度、IC 值区；值区 `[284, 3499)` |
| 3499 | 40 | 样例尾部，40 字节为 ASCII 十六进制字符；语义及校验算法待确认 |

准备函数直接跳过 6 字节段标识，制卡入口才逐个比较 `000PRN`、`000MAG` 和 `000EMV`。准备函数局部指针在 EMV 后跳过 40 字节，但对外游标按记录总长推进，也没有验证尾部。仅凭 40 个字符无法判断是摘要、校验值、签名的一部分还是其他字段。重写解析器先保存该尾部，按生产协议确认结果接入对应的验证步骤。

### 3.1 EMV 值区

依据 `HBW0001.cpp:459–498`、`READER.cpp:424–750` 与随附二进制样例。

| 样例偏移 | 字段 | 消费情况 |
| --- | --- | --- |
| 284 | 1 字节 AID 个数，样例 1 | 旧数组容量 5，拷贝前无个数检查 |
| 285 | 每项由 1 字节长度及 AID 值组成，样例 AID 长 8 | 保存到 `m_pbAID` 并包含长度前缀；HD01 Plus 安装使用首项 |
| 294 | 4 字节后续长度，样例 3201 | 源码跳过。样例中从该字段末尾到 EMV 末尾正好 3201 字节 |
| 298 | 2 字节清单长度 + DGI ID 列表，样例 82 字节、41 项 | 长度除以 2 得数据分组个数。ID 为 2 字节，旧代码只把清单转成文本用于日志等用途 |
| 382 | 2 字节清单长度 + 加密 DGI ID 列表，样例 18 字节、9 项 | 本入口跳过。实际应用写入的敏感分组由下游代码的固定分支决定 |
| 402 | 2 字节清单长度 + 日志 DGI ID 列表，样例长度 0 | 本入口跳过，历史日志仍会打印分组内容 |
| 404 | DGI 数据组，直到 3499 | 样例 41 组，顺序逐项与第一张清单一致，全部使用短长度 |

此处的 MIC 段标识、DGI ID 与组内 BER-TLV tag 分属不同层。DGI 自己的短格式由 2 字节 ID、1 字节长度和值组成，`bGetDGI` 按 `3 + valueLength` 前进。遇到长度首字节 `0xFF` 时，旧代码读后面的 2 字节，却只加 2。如果该扩展形式的长度只统计值，正确总步长应为 `5 + valueLength`。**待确认**扩展格式和声明长度语义。随附样例无扩展组，无法判定旧实现是否适配过其他长度约定。

`CARDDATA` 的旧长度检查发生在无容量拷贝之后，且用 `nDataLen/2` 传给解码函数，奇数长度的最后一个半字节会被截掉。应先验证封装完整性及 hex 偶数长度，再按记录、EMV、清单和 DGI 逐级建立受限子范围。

旧逻辑按清单长度得出的次数扫描数据，依据实际数据的 ID 分派到固定成员，未核对列表与分组顺序、重复、缺项或 EMV 末尾。未知 DGI 返回 `FALSE`。列表缓冲 `DGTTagData[512]` 存的是十六进制文本，其容量还需计入 NUL。新实现应保留有序 ID 和每组字节范围，为芯片与版本配置显式定义必需、可选和未知组的处理策略。样例的顺序一致可作为回归断言，生产是否强制顺序需由清单规范确认。

### 3.2 两份样例的交叉核对

二进制文件和 DOCX 内嵌的 `CARDDATA` 解码后均为 3539 字节。记录头与 EMV 值区到 DGI 起点之前逐字节相同。PRN、MAG、分组段和尾部分别存在 8、43、1434、38 个不同字节。两份均独立验证到 41 个短长度 DGI，ID 与各自的清单顺序一致，最后一组结束于 3499。两份都可用于检查分段边界。需要比较完整输入和预期输出时，必须给每份样例各自建立基准，并确认生产认可哪一份。

## 4. MakeCard_Run 的边界和处理顺序

### 4.1 导出接口

`HBW0001.def` 按名称导出 `MakeCard_Run`。旧声明见 `HBW0001.cpp:578`，回调 typedef 见 `CExterFuntion.h:9–10`。

| 参数 | 当前行为及迁移要点 |
| --- | --- |
| `cWorkData` | 注释定义首字节为读写器类型。入口未复制调用参数，回调实际收到 `CREADER` 内部清零的 128 字节数组。确认产线是否需要传递该字段 |
| `nChannelID` | 32 位值，传入读卡和日志回调及 HSM 日志侧。样例 EXE 直接传读卡句柄；产线也可能约定逻辑读卡器编号 |
| `pWriteCard` | 读卡回调，命令与响应使用 ASCII hex，长度是字符数；旧接口缺少响应容量参数 |
| `pWriteLog` | 日志回调，携带通道、级别、模块、状态和错误文本。入口直接调用，未判空 |
| `pData` | NUL 终止的 `CARDDATA` 封装，缺少显式长度 |
| `pDataRFU` | 本路径转交但未消费，EXE 传入清零缓冲 |
| `pDataRecv` | HSM 连接失败分支写网络诊断；成功路径未产出成品数据或发卡回执 |
| `cErrTxt` | 入口及部分校验路径写入可读文本，后续步骤多使用自己的局部错误文本。接口没有提供容量 |

`CREADER::CardCommand` 把传输结果和卡片状态字分别检查。旧路径会处理 `61xx`、`6Cxx`，样例 `RunCmd` 也有 `61xx` 处理，需确认到底由哪一层承担后续交换。样例 `RunAPDU` 的 RESET 分支为空。新接口可以使用原始字节、显式长度和容量，旧 ASCII hex 约定留在适配器。保留卡片 SW、设备错误码和制卡阶段，避免将不同故障折成同一个字符串。

### 4.2 配置与写卡阶段

`CREADER` 在回调绑定之前构造，尝试定位模块同目录的 `Hsm.ini` 并加载旧国密 DLL。路径失败分支可能在日志回调尚未就绪时调用它。随后入口绑定回调和通道，读取 `[server]` 下的 `ConnectType`、`ChipType`、`EDKey`、`TKey` 和 `SMTKey`，即使离线也要求三个配置项非空。与准备步骤的默认值 0 不同，制卡入口的 `ConnectType` 缺省为 1。

随附 INI 的 `ConnectType=0`、`ChipType=2` 和当前 HD01 Plus 分支匹配。源码 `ChipType` 缺省为 3，主链只接受 `HD01_Plus_CARD=2`，同方分支被注释。项目定制需求表写的是 `CIU9872B_01 plus_V0293`，并写有借记、电子现金及 QPBOC。**待确认**量产卡 COS、卡基预装状态和枚举的正式对应关系。

| 顺序 | 当前实现 | 入口返回 |
| ---: | --- | --- |
| 1 | 读配置，三个必要键任一为空直接退出 | -1 |
| 2 | `ConnectType != 0` 时尝试连接 HSM | 2 |
| 3 | 提取 `CARDDATA`、检查长度、解码 ASCII hex | 11 |
| 4 | 检查 PRN、MAG、EMV 标识，定位 AID 和 DGI 清单 | 12 / 13 / 14 对应三个段标识 |
| 5 | `bGetDGI` 对组数据分类并整理应用字段 | 15（实际仅接住布尔假） |
| 6 | 检查芯片配置，执行 `dwInstall_HD01_Plus_JAVA` | 23（不支持芯片）或 17（安装阶段） |
| 7 | `dwInitEC` 准备接触目录；`dwInitQC` 准备非接触目录 | 18 / 19 |
| 8 | `dwInitDC_HD_JAVA` 处理借记应用，包括应用选择与认证、敏感 DGI 准备及分组写入 | 20 |
| 9 | `ConnectType != 0` 时运行 `dwSetCPLC` 和 `dwPutKey` | 21 / 22 |
| 10 | 各阶段均成功，返回时释放联机会话 | 0 |

- **模式冲突。** 入口注释区分模式 1 和 2 是否做收尾，实际只判断非零，所以两个模式都会走 CPLC 和换键。正式模式需明确写成枚举，并由银行及产线接口负责人确认。
- **错误吞掉。** `bGetDGI` 返回 `BOOL`，部分 HSM 失败分支返回 101，调用方 `!bGetDGIData` 将该值当作成功。安装函数中也有多条重复覆盖 `dwRet` 的调用。重写应明确每个阶段的强制成功条件，保留错误原因与状态字。阶段 16 在当前入口链中无返回点。
- **应用职责。** `dwInitEC` / `dwInitQC` 的实际操作是选择接触 / 非接触支付目录后写目录数据。两者分别构造目录记录，部分字段来自前一步得到的 AID 和应用标签。`bGetDGI` 还会从个别组抽取应用字段，部分组（如 `0101`）会在字段处理之后重新封装。因此写入数据既有原样保留的分组，也有生成或重组的分组。新核心应让解析结果与应用阶段生成的数据各自可单独验证。HD 借记应用有固定顺序的常规、敏感及条件写入槽位，敏感预处理实际调用 `bGetSecureDGI_THD`。函数名中的 THD 不能用来推导当前的芯片分支。DGI 与应用槽位的最终对应以该项目批准的个人化清单为准。
- **失败恢复。** 返回 17–22 时，卡片可能已被写过一部分。重写时应记录最远完成阶段以及失败类型，依据卡商给出的可重入点决定重试、复检或隔离。收到超时后不得直接假定写卡未发生。

## 5. 国密库接入

旧源码实际加载的文件名是 `SM2_SM3_SM4DLL.dll`。 `SM2_SM3_SM4DLL.cpp:26–64` 将 SM2、SM3、SM4 等导出绑定为全局函数指针，`READER.cpp:183–195` 按每个 `CREADER` 构造/析构加载和卸载，并忽略加载结果。这种资源归属在多通道并发时容易出现竞态。

本次追踪范围内可达的旧 DLL 调用点是 `READER.cpp:558`，离线模式中 `bGetDGI` 对 `9F1F` 处理时按 16 字节调用 SM4 解密原语。必须核对原语的数据表示、块模式、显式长度、密钥字节语义和失败契约。旧实现循环取整，重写需要在原语调用前按配置验证完整块并明确尾部规则。标签封装、裁剪和 TLV 重组属于业务层。联机分支调用 HSM 的国密解密接口，借记应用的敏感分组处理另有 HSM 和 3DES 路径，不能由链接自研国密库这一改动推导成同一算法。当前主链未定位到可达的 SM2 或 SM3 DLL 调用。其他芯片文件和注释里的调用应在启用对应流程时单独核对。

建议在 CMake 中链接已有库 target，封装明确的输入/输出、错误和长度契约。以合成数据做原语已知答案测试，以及标签处理到产物的比对测试。配置和日志使用逻辑密钥标识及结果码，避免复制源码内的密钥字面量，避免记录账号、磁道、敏感 DGI 内容和完整 APDU 数据。

## 6. x64 重写落点

| 位置 | 已定位的问题 | 重写约定 |
| --- | --- | --- |
| EXE/DLL 导出 | `GetRecordTotalNum` 首参声明不一致；`EMVDataList` 在 DLL 与 EXE 中重复定义，`pDataEmv` 分别为 9856 和 12000 字节且元素类型不同 | 如果主机仍需加载 DLL，以单头文件定义严格 C ABI，按名称导出旧入口。新增接口使用显式版本、长度与容量；内部 C++ 对象由本模块持有 |
| 读卡器 | `SCARDHANDLE` 在 `Open` 的 INT 返回及 `RunCmd` 的 int 形参缩窄 | 使用 `SCARDCONTEXT`、`SCARDHANDLE` 原生宽度。如果旧 ABI 的通道是 32 位，用通道号映射设备会话 |
| HSM | `m_Socket` 和 `iSockId` 为 int，且 `dwHsmConnect()` 用 DWORD 混合返回句柄和负错误码 | 保留 `SOCKET` 与 `INVALID_SOCKET` 语义，独立返回错误。用 RAII 管理 WinSock 初始化、连接及关闭，包括连接中途失败 |
| 文件与内存 | `ftell`、固定中转数组、原始游标与后置校验；部分 `strcpy/sprintf` 无容量 | 文件入口保留实际缓冲区长度，用 C++17 指针加尺寸的字节视图与受检游标，文件字段按 `uint32_t/uint16_t` 解释；先检查剩余再读取 |
| UI 和路径 | 旧工程用 MFC 窄字符字符串、当前进程全局句柄与全局记录 | 先建立可由 CLI/测试驱动的核心，Windows 路径采用宽字符或 `std::filesystem::path`。句柄和记录归属单次会话 |
| 诊断和安全 | 旧日志含 PAN、磁道、完整记录和 APDU 内容 | 诊断记录记录 ID、阶段、偏移、字段类别、状态和必要长度 |
| 编译链 | VC 工程只有 Win32 配置；当前 CLion `CMakeLists.txt` 为 C++17 的占位可执行程序 | 按需要建核心库、兼容 DLL、PC/SC 和 HSM 适配器。Windows 侧链接 Winscard 和 Ws2_32，验证宿主、DLL 和自研库位数一致；开启转换警告并重点核对句柄缩窄、整数溢出及结构体布局 |

如果需保留现有第三方 32 位制卡主机，先确认其 ABI 可否升级。Windows x64 进程不能直接加载 Win32 DLL，Win32 主机也不能直接加载 x64 DLL。支持双位数时，分别构建各位数产物，并各自运行调用方联调。64 位统一调用约定只解决寄存器和栈传参约定，结构体布局、导出名、长度和语义仍要显式验证。

### 6.1 建议的重写次序和验收

1. **只读解析。** 用源文件和 DOCX 样例分别验证各段字节区间和 41 组结构。增加合成输入覆盖截短记录、溢出长度、错 MIC、奇数 hex、缺标签、宽字符路径、列表错位及扩展 DGI。解析整个输入成功后才发布准备结果。
2. **兼容适配。** 校验生成的标签字符串、旧导出名和签名、字符数与字节数转换，以及各输出的容量。约定文档层与代码层分别怎样报告解析失败。
3. **写卡编排。** 用替身读卡器与替身 HSM 按阶段验证调用、错误传播、日志和资源释放。覆盖配置缺失、非支持芯片、联机失败、部分写卡以及恢复路径。用批准的测试卡与测试 HSM 验证卡基状态、目录和应用效果。
4. **密码库替换。** 建立自研库原语的接口对照，覆盖解密失败、异常块长度和标签处理结果。在确认测试工艺后验证线上和离线路径，逐一核对涉及的 3DES 与国密配置。
5. **设备与产线。** 核对读卡回调、卡片状态、HSM 模式、错误码和隔离策略。只有卡片写入、收尾和约定的成品验证都成功，才允许界面或产线状态变为已发卡。
